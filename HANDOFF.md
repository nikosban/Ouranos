## Movement system (`Assets/Scripts/Movement/`)

Each ship runs one fixed step (`ShipMovement`, 0.02 s fixed timestep):
route refresh → look-ahead steering → moving-ship avoidance → motor proposal → turn guard (a refused turn rebuilds the proposal along the previous heading with `ShipMotor.AlongHeading`) → translation guard → motor commit; the visual reads the result.

**Footprint** (Issue #24): a planar capsule on y = 0 whose center segment runs ±`FootprintHalfSegment` (5 u) along the heading, with radius `FootprintRadius` (2.5 u); `FootprintHalfLength` (7.5 u) is center to tip. `ShipMovement.SyncFootprint` sets the root `CapsuleCollider` from the profile (radius, height = 2 × half length, direction Z); the collider rotates with the kinematic body.

| Part | Responsibility |
| --- | --- |
| `MovementOrders` | The only order seam: `Move(destinationXZ)`, `Stop()`. A new order supersedes the old route. |
| `RoutePlanner` / `Route` | NavMesh path request for agent type `Ship`, the retained corner polyline, and monotonic progress. Missing or partial routes log a warning and stop the ship. `IsNavigable(from, to)` is a query-only NavMesh raycast for the same agent type. |
| `RouteRequestQueue` | Scene component; at most `MaxRequestsPerFrame` (2) synchronous path requests per rendered frame. |
| `Steering` | Look-ahead target `LookAheadDistance` along the route, crossing corners; backs off toward the ship if the straight shortcut lacks clearance (footprint capsule aligned with the shortcut, at radius + skin, against the `Obstacle` layer). |
| `MovingShipAvoidance` | Every `NeighborSampleInterval` (phases staggered across ships): bounded `OverlapSphereNonAlloc` on the `Ship` layer, skipping ships at ≤ 0.1 u/s; constant-velocity closest approach of the centers per neighbor; at that time the two capsule center segments (current headings) are compared, and the earliest imminent conflict (`0 < t ≤ PredictionHorizon`, segment distance < both radii + `SafetyMargin`) becomes the threat. Offsets the route target by `AvoidanceOffset` along the route's starboard/port normal (route direction = progress point → route target, independent of the ship's sideways motion), so the ship follows a corridor parallel to the route, on the side away from the threat (exact head-on: starboard for both, provisional); opposite side only if the preferred one lacks static clearance or NavMesh; neither → speed cap 0. Holds threat and side until the threat is behind along the route by both footprint half lengths, or it disappears, stops, leaves the search radius, or keeps separating without danger for `ThreatReleaseDelay`; a strictly earlier threat from another ship replaces it. After release the offset ramps linearly to 0 over `AvoidanceRecoveryTime`. Resets immediately when the route object changes (new order, stop, arrival). Never writes Transform, state, route or orders. Inspector readout: threat (name set only when a threat is adopted or replaced, cleared on release, recovery start or reset; never read per step), recovering, time/distance of closest approach, side, temporary target, speed cap, guard blocked, overflow. |
| `ShipMotor` | Authoritative XZ position, heading, forward speed. Turn ≤ `TurnRate·dt`; accel/decel limits; arrival cap `sqrt(2·Dec·max(0, remaining − ArrivalRadius))`; pure-pursuit turn-rate cap; optional `speedCap`. The desired speed is the minimum of these caps via two-argument `Mathf.Min` calls (the `params` overload allocated 48 B per ship per step). Writes the pose to a kinematic Rigidbody. `AlongHeading` rebuilds a proposal at another heading (same speed, forward displacement). Read-only `Blocked` (translation limited) and `TurnBlocked` (last turn refused). |
| `CollisionGuard` | Footprint queries against `Ship` and `Obstacle` layers, skipping the ship's own colliders. `ConstrainTurn`: overlap test of the rotated footprint at radius + half the skin; any hit refuses the turn (one step turns ≤ 1.8°, so the end pose bounds the sweep). `ConstrainMotion`: capsule cast aligned to the heading at radius + skin; returns permitted displacement and a blocked flag. A cast that starts touching blocks only motion toward the collider, measured from the nearest point of the ship's own segment. `HasClearance`: capsule aligned with the travel direction against static layers. Blocked motion keeps only the speed it actually moved. |
| `ShipVisual` | Applies `VisualAltitudeOffset` to the `Visual` child only. |
| `ShipMovementDebug` | Gizmos: capsule footprint outline (green, red when blocked), route corners (cyan), progress point (white), look-ahead target (yellow), avoidance target (magenta), threat line and predicted closest-approach positions (orange). Visible in the Scene view and in the Game view with Gizmos on. |

**Group Move** (`GroupMoveDispatcher.Move(ships, targetAnchor)`, static, stateless): skips null, destroyed, inactive and duplicate ships, snapshots each remaining ship's `Motor.State.Position`, computes `delta = targetAnchor − centroid`, and calls `Orders.Move(position + delta)` once per ship. Returns the `GroupMoveAssignment` list (ship, destination); zero valid ships logs a warning and issues nothing. The target anchor is the destination centroid. No rotation, slotting, leader, speed sync, waiting or persistent group state; the caller owns the ship set, and each ship's `MovementOrders.Destination` stays authoritative. A new group move takes a fresh snapshot and supersedes the ships' orders. Path requests go through `RouteRequestQueue` as usual; a failed route stops only that ship. Callers: `PlayerCommands` (two or more selected ships, one call per command) and `GroupMoveScenario`.

Arrival completes the order when the remaining route distance is ≤ `ArrivalRadius`. Avoidance keeps the route's remaining distance, so arrival is unaffected.

**Profiler markers** (Issue #7): `ShipMovement` wraps each fixed step in `Movement.FixedStep` (inclusive) with children `Movement.Steering`, `Movement.Avoidance`, `Movement.MotorPropose`, `Movement.Guard` (turn check and translation sweep since Issue #24), `Movement.MotorCommit`; `RouteRequestQueue` wraps each request in `Movement.RouteRequest` and exposes `PendingCount`. Markers only; the pipeline order is unchanged.

Inside `Movement.Avoidance` (Issue #9), three sibling markers that never nest: `Avoidance.NeighborQuery` (the `OverlapSphereNonAlloc` call), `Avoidance.NeighborScan` (the candidate loop with `Predict`), `Avoidance.SideClearance` (`SideIsClear`: `CollisionGuard.HasClearance` + `RoutePlanner.IsNavigable`). The rest of `Movement.Avoidance` (route direction, threat hold/adopt/release, `ApplySide`, readout) is reported as "Avoidance exclusive" = parent − the three children. `MovementPerformanceScenario` reports each child's step-frame median/p95/max and share of `Movement.Avoidance`, and its call count. Marker overhead was not measurable (see Last result).

## Tactical camera (`Assets/Scripts/Camera/`, namespace `Ouranos.Cameras`)

| Part | Responsibility |
| --- | --- |
| `TacticalCameraController` | On the camera object. Exclusively owns `focalXZ`, `yawDegrees` and `distance` (serialized focal/yaw are the initial values; distance starts at `InitialDistance`, clamped). Each `LateUpdate` polls its local serialized `InputAction` fields with `Time.deltaTime`, then derives the Transform: rotation `Euler(45, yaw, 0)`, position `ToWorld(focal) − forward · distance`, so the viewport-center ray always meets Y = 0 at the focal point. Pan: WASD, normalized, rotated by yaw onto XZ. Yaw: Q −/E + at `KeyboardYawSpeed`, plus horizontal `<Mouse>/delta/x` while the middle button is held; vertical motion is never read; yaw wraps to [0, 360); positive turns clockwise seen from above (provisional convention). Zoom: each wheel notch multiplies distance by (1 − `WheelZoomFraction`) inward and divides outward (wheel units normalized by `InputSystem.settings.scrollDeltaBehavior`); `equals`/`numpadPlus` in, `minus`/`numpadMinus` out at `KeyZoomSpeed`; clamped to Min/Max. Composite bindings are created in `Reset` (a field initializer would start the Input System from a MonoBehaviour constructor, which the player rejects). Focus and follow (Issue #14): optional read-only `Selection` (`ShipSelection`); without it F does nothing. `FocusFollow` (`<Keyboard>/f`) with ≥ 1 selectable selected ship sets the focal point to their `Motor.State.Position` centroid, sets `Following`, and zooms out only if needed so every selected center projects inside the viewport shrunk by `FrameMargin` per edge (closed-form fit for the current yaw, 45° pitch, field of view and aspect; clamped to Min/Max; never zooms in). Pressing F again recenters and reframes; it does not stop follow. While `Following`, each `LateUpdate` sets the focal point to the live centroid of the current selection (no smoothing, no cache); a selection change tracks the new centroid without reframing; an empty selection ends follow and leaves the focal point where it is. Any non-zero WASD pan input ends follow and pans in the same frame; yaw and zoom never end it. Order in `LateUpdate`: yaw, pan (cancels follow), zoom, F/follow, Transform. Read-only `FocalPoint`, `Yaw`, `Distance`, `Following`; `Focus(Vector2)` sets the focal point (overwritten next frame while following). Never touches ships, orders, NavMesh, collision or other cameras; never writes the selection; others must use `Focus`, not the Transform. The projection is the scene's `Camera` setting. |
| `CameraAcceptanceScenario` | Acceptance only (see Test scenes). Execution order 100, measures in `LateUpdate` after the controller. Owns all acceptance state (coverage, results, virtual devices); the controller holds none. |

## Test scenes

`Assets/Scenes/MovementTest.unity`: floor, static obstacle (radius 10 at origin), Ship A (-40, 0) facing +X, Ship B (30, 0) facing −X, baked `Navigation` NavMeshSurface (ships excluded), `Movement Acceptance Scenario`.

Press Play: the scenario orders A to (15, 0), then to (40, 0), and shows PASS/FAIL per criterion in its Inspector fields, on screen, and as `[Acceptance]` log lines. ## Known limitations and debt

- The capsule footprint approximates the 5 × 15 box hull (accepted placeholder debt, owner F1): each corner sticks out 1.04 u beyond the end caps, so hulls overlap visually at contact while capsules stay clear. Measured: −1.39 u in the 90° crossing, −0.94 u stern quarter against an obstacle, −0.40 u bow corner turning away from contact. Routes ignore turn radius.
- Turn refusal can pin a ship beside an obstacle (known limitation, owner F2): a forward-only 15 u ship tangent to an obstacle that must turn toward it makes legal partial turns until the bow is close, then every turn toward it is refused and forward motion along the inward heading is blocked, permanently (39 s in `ElongatedFootprintTest` Case 4). Nothing reverses or turns away; recovery needs its own owner ticket.
- The 90° crossing of two 15 u ships deadlocks (known limitation, owner F3): one 4 u avoidance offset per ship does not clear long hulls; the bows meet and each blocks the other's forward motion (23.5 s to the limit in Case 3). Passing/yielding and avoidance sizing for long hulls need their own owner ticket.
- The turn check inflates by half the skin, so turns may leave a gap between half and the full skin (0.026 u measured); the next forward sweep then starts touching and blocks motion toward the contact.
- The NavMesh is orientation-blind: agent radius 3.0 covers the width only, not the 15 u length or the heading; `CollisionGuard` alone enforces occupancy. `HasClearance` assumes the heading equals the shortcut direction, while the real heading lags it.
- `Predict` compares capsule segments only at the centers' closest-approach time; the true capsule minimum can occur at another time. `ClosestDistance` (and the benchmark's "min predicted closest approach") is now a segment distance.
- `ElongatedFootprintTest` Case 6 exercises the start-touching "toward" branch (approach) but not its "away" branch: after the escape order the turn opens the gap faster than the ship closes it, so translation is never refused.
- Selection rings (`FootprintRadius` + 1 = 3.5 u) sit inside the 15 u hull; box selection and F framing use ship centers (Issue #24 Q4, unchanged).
- One NavMesh agent type means one baked clearance; other ship radii need their own agent types and bakes.
- Ships are not in the NavMesh; a ship blocked by a stopped ship waits in place with no recovery (avoidance ignores ships at ≤ 0.1 u/s).
- Avoidance predicts at constant current velocity (no anticipated turns or acceleration) and handles one threat at a time. Head-on and the opposite-direction side-by-side pass are verified; the 90° crossing deadlocks with long hulls (see above); near-parallel same-direction and multi-ship traffic are untested.
- The neighbor buffer is bounded; when it fills, `Overflowed` is set, `OverflowCount` increments, and some neighbors may be missed. Hard blocking is the fallback.
- If the held side loses static clearance mid-encounter, the ship brakes instead of switching sides.
- The corridor offset is a fixed `AvoidanceOffset`, not sized to the threat. At 4 u the head-on pass keeps 7.8 u between centers; the final clearance is an owner feel choice.
- Ships finish recovery with a small lateral residual (0.17 u in the head-on test). A pass that ends near the destination can arrive further off the route.
- Neighbor states may be up to one fixed step old, because ships' FixedUpdate order is undefined.
- Look-ahead shortcuts are checked at footprint + skin, so ships can ride the exact collision clearance rather than the NavMesh's 0.5 u margin.
- Forward-only thrust with capped turning is a reversible prototype assumption; final handling/strafe behavior is UNDECIDED (owner).
- Pose writes teleport the kinematic body each step; no render interpolation.
- Gizmos debug view exists only in the Editor.
- Group Move preserves the arrangement only in the assigned destinations. Final positions differ by the arrival radius (about 1.9 u short along each route) or NavMesh snapping; a failed ship is reported, not re-slotted. Congested arrivals and overlapping starts are not handled.
- Performance is measured on one desktop machine in a Development Player only. Target hardware, frame-rate budget and supported fleet size are UNDECIDED (owner); the numbers are not a shipping claim.
- `Movement.Avoidance` is the largest movement cost at 100 ships (about 34% in the Issue #24 probe, 40% in Issue #9), closely followed by `Movement.Guard` (29%, turn check plus capsule sweep), and total movement crosses the Issue #7 gate (p95 ≥ 0.5 ms per rendered frame at 100 ships). No CPU-path optimization has been made or approved; any change needs its own measured proposal and review.
- The benchmark with 15 u hulls is congested (Issue #24 probe: 59.2% moving, 51 sustained blockers within each group's lane, longest 30.9 s), and the outermost sterns spawn up to 1.69 u outside the NavMesh edge (inside the floor). It has no current baseline (F4).
- One 28 B string per threat adoption or replacement remains (Inspector readout). At 100 ships adoptions run at 1,256–1,360 per 33 s against about 110 activations, so held threats are replaced often in dense same-lane traffic. This is a behavior observation, not a measured problem.
- After a held threat is destroyed or deactivated, `ThreatName` shows its old name until the next evaluation (≤ `NeighborSampleInterval`, measured 0.10 s).
- A ship whose `ShipMovement` component is disabled while its collider stays enabled keeps its last motor speed, so other ships still treat it as a moving threat. In the `AvoidanceTest` check, A held the frozen B for about 6.4 s until it was blocked against it. Pre-existing threat-selection behavior; not changed (Issue #9 review).
- At 50 and 100 ships the 16-slot neighbor buffer overflows on nearly every avoidance evaluation in the benchmark, so some neighbors are missed; hard blocking is the fallback.
- Dense head-on traffic deadlocks: opposing 5-column streams on one line, or lanes overlapping (`LaneOffset` ≤ 50 u), leave ships blocked for 20 s or more at every Count, because a ship blocked by a stopped ship has no recovery. This is movement-behavior debt, separate from performance. The benchmark avoids it with 60 u lanes, so it measures same-lane encounters, not head-on ones.
- Route-request latency follows the 2-per-frame budget: a 100-ship command needs 49 rendered frames (about 0.7 s at 60 fps after startup) until the last route is ready.
- The selection rings and drag rectangle are placeholder art; final appearance is UNDECIDED (owner).
- Box membership uses the projected ship center only (Issue #13 debt): a large ship partly inside the box is missed. Revisit if player QA finds missed silhouettes. Shift-drag replaces the set (provisional).
- Box selection queries all `ShipMovement` objects once per drag release; not measured at fleet scale.
- A single click now selects on button release, not press (needed to tell clicks from drags).
- `MovementOrders` has no order counter, so the group acceptance cannot detect an identical repeated `Move` to a ship's own destination.
- A destroyed or deactivated selected ship stays in the selection until the next `SetSingle`, `Toggle`, `SetMany` or `Clear`; commands skip it and its ring hides.
- Right-clicking over a ship or obstacle orders the ground point beneath (ground mask only); there is no attack/follow or UI-over-pointer blocking.
- The unused project-wide template `InputSystem_Actions` binds `S` (`Player/Move`), `E` (`Player/Interact`) and `C` (`Player/Crouch`); nothing reads it. Revisit when shared controls are introduced.
- Scripted input events are only processed while the player window has focus (`runInBackground` off).
- `Assets/TutorialInfo/Icons/URP.png` is damaged in the working tree (not part of any change).
- The tactical camera has no map bounds and no camera collision (Issue #12 debt; until a real level needs it).
- Player and camera bindings are separate local actions with no input router; the S conflict was resolved by moving Stop to C (owner). Any new binding must be checked against both by hand.
- Camera keyboard paths are physical key positions (US layout names): the main-row zoom-in key is the `=`/`+` key.
- Camera pan speed is constant in world units at every zoom distance; the yaw direction convention (E and rightward drag clockwise from above) is provisional; final camera feel is UNDECIDED (owner).
- The camera rate check divides displacement by summed frame time, so it confirms delta-time scaling; it is not a wall-clock measurement.
- `CameraTest`'s pan-direction check (1°) is only meaningful at capped frame rates: run uncapped (about 950 fps, 0.014 u per frame) it measured 4.6° from float noise in the center-ray ground point; at 30/60/144 fps it measures 0.08–0.55°. Always run it with `-cameraFps`.
- Follow is a hard snap to the centroid every frame (no smoothing). F framing uses ship centers only, like box selection, so large hulls can extend past the 80 % frame; if the ships do not fit at `MaxDistance`, the distance stays at the maximum.
