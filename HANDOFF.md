# HANDOFF

## Project state

- Unity 6000.6.4f1, URP 17.6.0, Input System 1.20.0.
- Unity AI Navigation `com.unity.ai.navigation` 2.0.16.
- One gameplay system: 2.5D ship movement with physical blocking (Issue #1), predictive avoidance between moving ships (Issue #3), and Group Move by translated destinations (Issue #5).
- Movement performance profiled at 10/50/100 ships with a dedicated benchmark scene and profiler markers (Issue #7); one measured allocation removed.
- Avoidance cost sub-attributed with three submarkers, and the per-step threat-name readout allocation removed (Issue #9).
- Player control: click, Shift-click and drag-box selection of one or more ships, right-click Move (one ship) or Group Move (two or more, through `GroupMoveDispatcher`) and C Stop, with placeholder selection rings and drag rectangle (Issues #11, #13).
- Tactical camera: perspective, fixed 45° pitch, WASD pan, wheel and +/- zoom, Q/E and middle-mouse yaw orbit around a ground focal point (Issue #12). F focuses, frames and follows the selected ships; WASD cancels follow (Issue #14). Used in `CameraTest`, `GroupPlayerControlTest` and `TacticalCameraSelectionTest`.
- Order feedback: a provisional circle at each selected ship's active Move destination (Issue #14).

## Decisions

From the Issue #1 decision log:

- DECIDED: Ouranos uses 2.5D navigation on XZ with cosmetic altitude variation. Navigation stays planar and visuals stay independent.
- DECIDED: Ships and obstacles physically block movement; ships avoid or stop, never pass through occupied space.
- DECIDED: Intermediate path waypoints guide continuous look-ahead steering and are not stop destinations.
- DECIDED: The movement system is built in independently verifiable vertical slices, starting with single-ship movement and blocking.
- DECIDED: Acceptance for movement slices is an in-game scenario with recorded metrics, not automated PlayMode tests (Issue #1 review).

From the Issue #3 decision log:

- DECIDED: Predictive moving-ship avoidance is a temporary steering/speed adjustment before ShipMotor, while CollisionGuard remains the final blocking authority.
- DECIDED: Avoidance begins with bounded local nearest-approach prediction, not a global multi-agent solver.

From the Issue #5 decision log:

- DECIDED: Group Move assigns each selected ship a destination obtained by translating its current XZ position by the group's centroid-to-target displacement, with no rotation. — Preserve the initial arrangement at the commanded destination, not during travel.
- DECIDED: Group Move issues independent per-ship orders with no speed synchronization, waiting or persistent formation constraints. — Group movement and formations are separate components.
- DECIDED: Persistent coordinated formations, including wedge layouts and in-transit relative-position maintenance, are a later independent system. — Keep the group command dispatcher minimal.

From the Issue #7 decision log:

- DECIDED: Stage 4 profiles movement at scale before optimizing, and changes only measured bottlenecks while preserving gameplay. — Avoid speculative rewrites and keep movement behavior stable.
- DECIDED: Performance profiling precedes ship selection UX and persistent formations. — Establish the scaling baseline before adding more gameplay systems.
- DECIDED: Movement benchmarks run in a Windows Development Player capped at 60 fps (VSync off), reporting per-rendered-frame and per-step-frame costs (Issue #7 review).
- DECIDED: Benchmark traffic uses opposing lanes offset by `LaneOffset` 60 u; overlapping head-on lanes deadlock and were rejected as the baseline (Issue #7 owner decision).

From the Issue #9 decision log:

- DECIDED: Avoidance performance refinement removes confirmed debug-readout allocations and profiles existing hot paths before changing behavior. — Measured local fixes beat speculative algorithms and added per-step work.
- DECIDED: Dense ship traffic, passing and deadlock recovery remain separate gameplay decisions, not performance fixes. — Profiling must not determine how fleets are allowed to move.

From the Issue #11 decision log:

- DECIDED: Player picking and input live in `Selection`/`Interaction`, never in `ShipMovement`. — Keeps simulation independent of local player controls.
- DECIDED: Input bindings for Task 6 are local serialized `InputAction` fields on `PlayerCommands`; the shared `InputSystem_Actions` template is not modified. — One consumer exists.
- DECIDED: Scripted input is confined to acceptance verification and drives the real bindings through virtual devices. — No second command path.
- DECIDED: The scripted 0.1 u destination check is authoritative; the manual 1.0 u marker-radius check is supplementary and reported separately.

From the Issue #13 decision log:

- DECIDED: Stop uses C for player commands and the tactical camera retains WASD panning. — Owner control choice resolves the previous S conflict.
- DECIDED: The box rendering view remains in Interaction; it reads gesture state without owning selection. — Keeps the dependency one-way.
- DECIDED: Task 8 reruns PlayerControlTest after changing player controls. — Existing single-selection behavior must remain intact.
- Provisional (ticket): box membership is the ship's projected center; Shift-drag replaces the set like a plain drag.

From the Issue #14 decision log:

- DECIDED: F focuses, frames and continuously follows the current selection; it does not toggle off. — Owner specifies one action; WASD alone cancels manual tracking.
- DECIDED: Keep the small, provisional destination circle in Task 9. — Owner confirms its scope; it reads active Move orders and has no camera-control dependency.
- DECIDED: Focus zooms out only if needed to fit the projected selection; no automatic zoom-in. — Preserves the chosen zoom while meeting the framing goal.
- DECIDED: Share a small ring-line renderer helper between selection indicators and destination feedback. — Two concrete consumers justify extraction.

From the Issue #12 decision log:

- DECIDED: The tactical camera is perspective with a fixed 45° downward pitch and yaw-only orbit (owner).
- DECIDED: Tactical zoom may update distance without a redundant ground raycast, while acceptance verifies the viewport-center ground point independently. — The fixed 45° camera geometry makes the center intersection invariant.
- DECIDED: The camera lives in `Assets/Scripts/Camera/` under namespace `Ouranos.Cameras`. — Avoids the existing `Camera` symbol collision.
- DECIDED: Camera scripted input is optional acceptance-only tooling, off in the committed scene. — Reuses the already accepted verification pattern without a second gameplay input path.

## Movement system (`Assets/Scripts/Movement/`)

Each ship runs one fixed step (`ShipMovement`, 0.02 s fixed timestep):
route refresh → look-ahead steering → moving-ship avoidance → motor proposal → collision guard → motor commit; the visual reads the result.

| Part | Responsibility |
| --- | --- |
| `MovementOrders` | The only order seam: `Move(destinationXZ)`, `Stop()`. A new order supersedes the old route. |
| `RoutePlanner` / `Route` | NavMesh path request for agent type `Ship`, the retained corner polyline, and monotonic progress. Missing or partial routes log a warning and stop the ship. `IsNavigable(from, to)` is a query-only NavMesh raycast for the same agent type. |
| `RouteRequestQueue` | Scene component; at most `MaxRequestsPerFrame` (2) synchronous path requests per rendered frame. |
| `Steering` | Look-ahead target `LookAheadDistance` along the route, crossing corners; backs off toward the ship if the straight shortcut lacks clearance (capsule cast at footprint + skin against the `Obstacle` layer). |
| `MovingShipAvoidance` | Every `NeighborSampleInterval` (phases staggered across ships): bounded `OverlapSphereNonAlloc` on the `Ship` layer, skipping ships at ≤ 0.1 u/s; constant-velocity closest approach per neighbor; the earliest imminent conflict (`0 < t ≤ PredictionHorizon`, distance < both footprints + `SafetyMargin`) becomes the threat. Offsets the route target by `AvoidanceOffset` along the route's starboard/port normal (route direction = progress point → route target, independent of the ship's sideways motion), so the ship follows a corridor parallel to the route, on the side away from the threat (exact head-on: starboard for both, provisional); opposite side only if the preferred one lacks static clearance or NavMesh; neither → speed cap 0. Holds threat and side until the threat is behind along the route by both footprints, or it disappears, stops, leaves the search radius, or keeps separating without danger for `ThreatReleaseDelay`; a strictly earlier threat from another ship replaces it. After release the offset ramps linearly to 0 over `AvoidanceRecoveryTime`. Resets immediately when the route object changes (new order, stop, arrival). Never writes Transform, state, route or orders. Inspector readout: threat (name set only when a threat is adopted or replaced, cleared on release, recovery start or reset; never read per step), recovering, time/distance of closest approach, side, temporary target, speed cap, guard blocked, overflow. |
| `ShipMotor` | Authoritative XZ position, heading, forward speed. Turn ≤ `TurnRate·dt`; accel/decel limits; arrival cap `sqrt(2·Dec·max(0, remaining − ArrivalRadius))`; pure-pursuit turn-rate cap; optional `speedCap`. The desired speed is the minimum of these caps via two-argument `Mathf.Min` calls (the `params` overload allocated 48 B per ship per step). Writes the pose to a kinematic Rigidbody. |
| `CollisionGuard` | Swept vertical-capsule query (footprint + skin) against `Ship` and `Obstacle` layers; returns permitted displacement and a blocked flag. Blocked motion keeps only the speed it actually moved. |
| `ShipVisual` | Applies `VisualAltitudeOffset` to the `Visual` child only. |
| `ShipMovementDebug` | Gizmos: footprint (green, red when blocked), route corners (cyan), progress point (white), look-ahead target (yellow), avoidance target (magenta), threat line and predicted closest-approach positions (orange). Visible in the Scene view and in the Game view with Gizmos on. |

**Group Move** (`GroupMoveDispatcher.Move(ships, targetAnchor)`, static, stateless): skips null, destroyed, inactive and duplicate ships, snapshots each remaining ship's `Motor.State.Position`, computes `delta = targetAnchor − centroid`, and calls `Orders.Move(position + delta)` once per ship. Returns the `GroupMoveAssignment` list (ship, destination); zero valid ships logs a warning and issues nothing. The target anchor is the destination centroid. No rotation, slotting, leader, speed sync, waiting or persistent group state; the caller owns the ship set, and each ship's `MovementOrders.Destination` stays authoritative. A new group move takes a fresh snapshot and supersedes the ships' orders. Path requests go through `RouteRequestQueue` as usual; a failed route stops only that ship. Callers: `PlayerCommands` (two or more selected ships, one call per command) and `GroupMoveScenario`.

Arrival completes the order when the remaining route distance is ≤ `ArrivalRadius`. Avoidance keeps the route's remaining distance, so arrival is unaffected.

**Profiler markers** (Issue #7): `ShipMovement` wraps each fixed step in `Movement.FixedStep` (inclusive) with children `Movement.Steering`, `Movement.Avoidance`, `Movement.MotorPropose`, `Movement.Guard`, `Movement.MotorCommit`; `RouteRequestQueue` wraps each request in `Movement.RouteRequest` and exposes `PendingCount`. Markers only; the pipeline order is unchanged.

Inside `Movement.Avoidance` (Issue #9), three sibling markers that never nest: `Avoidance.NeighborQuery` (the `OverlapSphereNonAlloc` call), `Avoidance.NeighborScan` (the candidate loop with `Predict`), `Avoidance.SideClearance` (`SideIsClear`: `CollisionGuard.HasClearance` + `RoutePlanner.IsNavigable`). The rest of `Movement.Avoidance` (route direction, threat hold/adopt/release, `ApplySide`, readout) is reported as "Avoidance exclusive" = parent − the three children. `MovementPerformanceScenario` reports each child's step-frame median/p95/max and share of `Movement.Avoidance`, and its call count. Marker overhead was not measurable (see Last result).

## Player control (`Assets/Scripts/Selection/`, `Assets/Scripts/Interaction/`)

| Part | Responsibility |
| --- | --- |
| `ShipSelection` | Scene component; the only owner of the selected set (unique selectable ships, any count). `IReadOnlyList<ShipMovement> Selected`; `SetSingle(ship)` (ignores non-selectable ships; re-selecting is a no-op), `Toggle(ship)` (adds or removes a selectable ship), `SetMany(ships)` (replaces with the unique selectable ones; none clears), `Clear()`. `SetSingle`/`Toggle` first drop entries no longer selectable. `IsSelectable`: not null, active and enabled. Never touches orders. |
| `PlayerCommands` | Local player input → selection and orders. Requires explicit `Camera` and `Selection` references; if either is missing it logs an error and disables itself. `Select` (LMB) is one gesture: press records the position and pointer device; while held, `Update` refreshes the read-only `IsDragging` (moved > `DragThreshold`) and `DragRect` (screen pixels, bottom-left origin, any drag direction); release resolves it. Click: raycast on `ShipLayers`; a selectable ship → `Toggle` with `AddModifier` (Shift) held, else `SetSingle`; anything else → `Clear`, or no change with Shift. Drag: `SetMany` of the selectable ships on `ShipLayers` whose `ToWorld(Motor.State.Position)` projects inside the rectangle in front of the camera (candidates from one `FindObjectsByType<ShipMovement>()` per release); an empty box clears; Shift is ignored. `Command` (RMB): raycast on `GroundLayers`; one selectable selected ship → `Orders.Move(hit XZ)`, two or more → one `GroupMoveDispatcher.Move(ships, hit XZ)`; a ground miss logs and issues nothing. `Stop` (C): `Orders.Stop()` on selected ships. Changing selection never changes orders. |
| `SelectionIndicator` | Provisional placeholder: one ring per selectable selected ship (`FootprintRadius + RadiusMargin`). Its own `LineRenderer` draws the first ring and is the configuration source; further rings are runtime children carrying only a `LineRenderer` with the same material and settings, created on demand and hidden when unused. Reads selection only; ships untouched. |
| `SelectionBoxView` (`Interaction/`) | Provisional placeholder: while `PlayerCommands.IsDragging`, draws `DragRect` as an IMGUI fill and border. Reads `PlayerCommands` only. |
| `GroupPlayerControlScenario` | Acceptance only (see Test scenes). |
| `RingLines` (`Selection/`) | Static helper shared by `SelectionIndicator` and `OrderFeedback`: `Prepare` (world-space closed ring, no shadows, hidden), `CreateLike` (child object carrying only a `LineRenderer` copied from a source renderer), `Draw` (ring around an XZ center at a height). No marker logic. |
| `OrderFeedback` (`Interaction/`) | Provisional placeholder: a circle at `Orders.Destination` for every selectable selected ship whose `Orders.Kind` is `Move`; Stop and None show nothing; unselected ships show nothing. Its own `LineRenderer` is the configuration source; further circles via `RingLines`. Reads `ShipSelection` and `MovementOrders` only; no command state; never writes orders, selection or the camera. |
| `PlayerControlScenario` | Acceptance only (see Test scenes). |

## Tactical camera (`Assets/Scripts/Camera/`, namespace `Ouranos.Cameras`)

| Part | Responsibility |
| --- | --- |
| `TacticalCameraController` | On the camera object. Exclusively owns `focalXZ`, `yawDegrees` and `distance` (serialized focal/yaw are the initial values; distance starts at `InitialDistance`, clamped). Each `LateUpdate` polls its local serialized `InputAction` fields with `Time.deltaTime`, then derives the Transform: rotation `Euler(45, yaw, 0)`, position `ToWorld(focal) − forward · distance`, so the viewport-center ray always meets Y = 0 at the focal point. Pan: WASD, normalized, rotated by yaw onto XZ. Yaw: Q −/E + at `KeyboardYawSpeed`, plus horizontal `<Mouse>/delta/x` while the middle button is held; vertical motion is never read; yaw wraps to [0, 360); positive turns clockwise seen from above (provisional convention). Zoom: each wheel notch multiplies distance by (1 − `WheelZoomFraction`) inward and divides outward (wheel units normalized by `InputSystem.settings.scrollDeltaBehavior`); `equals`/`numpadPlus` in, `minus`/`numpadMinus` out at `KeyZoomSpeed`; clamped to Min/Max. Composite bindings are created in `Reset` (a field initializer would start the Input System from a MonoBehaviour constructor, which the player rejects). Focus and follow (Issue #14): optional read-only `Selection` (`ShipSelection`); without it F does nothing. `FocusFollow` (`<Keyboard>/f`) with ≥ 1 selectable selected ship sets the focal point to their `Motor.State.Position` centroid, sets `Following`, and zooms out only if needed so every selected center projects inside the viewport shrunk by `FrameMargin` per edge (closed-form fit for the current yaw, 45° pitch, field of view and aspect; clamped to Min/Max; never zooms in). Pressing F again recenters and reframes; it does not stop follow. While `Following`, each `LateUpdate` sets the focal point to the live centroid of the current selection (no smoothing, no cache); a selection change tracks the new centroid without reframing; an empty selection ends follow and leaves the focal point where it is. Any non-zero WASD pan input ends follow and pans in the same frame; yaw and zoom never end it. Order in `LateUpdate`: yaw, pan (cancels follow), zoom, F/follow, Transform. Read-only `FocalPoint`, `Yaw`, `Distance`, `Following`; `Focus(Vector2)` sets the focal point (overwritten next frame while following). Never touches ships, orders, NavMesh, collision or other cameras; never writes the selection; others must use `Focus`, not the Transform. The projection is the scene's `Camera` setting. |
| `CameraAcceptanceScenario` | Acceptance only (see Test scenes). Execution order 100, measures in `LateUpdate` after the controller. Owns all acceptance state (coverage, results, virtual devices); the controller holds none. |

## Known limitations and debt

- Circular footprints approximate hulls; routes ignore turn radius.
- One NavMesh agent type means one baked clearance; other ship radii need their own agent types and bakes.
- Ships are not in the NavMesh; a ship blocked by a stopped ship waits in place with no recovery (avoidance ignores ships at ≤ 0.1 u/s).
- Avoidance predicts at constant current velocity (no anticipated turns or acceleration) and handles one threat at a time. Only the head-on case is verified; crossing, near-parallel and multi-ship traffic are untested.
- The neighbor buffer is bounded; when it fills, `Overflowed` is set, `OverflowCount` increments, and some neighbors may be missed. Hard blocking is the fallback.
- If the held side loses static clearance mid-encounter, the ship brakes instead of switching sides.
- The corridor offset is a fixed `AvoidanceOffset`, not sized to the threat. At 4 u the head-on pass keeps 7.8 u between centers; the final clearance is an owner feel choice.
- Ships finish recovery with a small lateral residual (0.17 u in the head-on test). A pass that ends near the destination can arrive further off the route.
- Neighbor states may be up to one fixed step old, because ships' FixedUpdate order is undefined.
- Look-ahead shortcuts are checked at footprint + skin, so ships can ride the exact collision clearance (12.05 u from the test obstacle) rather than the NavMesh's 0.5 u margin.
- Forward-only thrust with capped turning is a reversible prototype assumption; final handling/strafe behavior is UNDECIDED (owner).
- Pose writes teleport the kinematic body each step; no render interpolation.
- Gizmos debug view exists only in the Editor.
- Group Move preserves the arrangement only in the assigned destinations. Final positions differ by the arrival radius (about 1.9 u short along each route) or NavMesh snapping; a failed ship is reported, not re-slotted. Congested arrivals and overlapping starts are not handled.
- Performance is measured on one desktop machine in a Development Player only. Target hardware, frame-rate budget and supported fleet size are UNDECIDED (owner); the numbers are not a shipping claim.
- `Movement.Avoidance` is the largest movement cost at 50–100 ships (about 40%), and total movement still crosses the Issue #7 gate (p95 ≥ 0.5 ms per rendered frame at 100 ships). Its dominant child is `Avoidance.NeighborScan` (about 58%). No CPU-path optimization has been made or approved; any change needs its own measured proposal and review.
- One 28 B string per threat adoption or replacement remains (Inspector readout). At 100 ships adoptions run at 1,256–1,360 per 33 s against about 110 activations, so held threats are replaced often in dense same-lane traffic. This is a behavior observation, not a measured problem.
- After a held threat is destroyed or deactivated, `ThreatName` shows its old name until the next evaluation (≤ `NeighborSampleInterval`, measured 0.10 s).
- A ship whose `ShipMovement` component is disabled while its collider stays enabled keeps its last motor speed, so other ships still treat it as a moving threat. In the `AvoidanceTest` check, A held the frozen B for about 6.4 s until it was blocked against it. Pre-existing threat-selection behavior; not changed (Issue #9 review).
- At 50 and 100 ships the 16-slot neighbor buffer overflows on nearly every avoidance evaluation in the benchmark, so some neighbors are missed; hard blocking is the fallback.
- Dense head-on traffic deadlocks: opposing 5-column streams on one line, or lanes overlapping (`LaneOffset` ≤ 50 u), leave ships blocked for 20 s or more at every Count, because a ship blocked by a stopped ship has no recovery. This is movement-behavior debt, separate from performance. The benchmark avoids it with 60 u lanes, so it measures same-lane encounters, not head-on ones.
- Route-request latency follows the 2-per-frame budget: a 100-ship command needs 49 rendered frames (about 0.7 s at 60 fps after startup) until the last route is ready.
- The selection rings and drag rectangle are placeholder art; final appearance is UNDECIDED (owner).
- Box membership uses the projected ship center only (Issue #13 debt): a large ship partly inside the box is missed. Revisit if player QA finds missed silhouettes. Shift-drag replaces the set (provisional).
- Box selection queries all `ShipMovement` objects once per drag release; not measured at fleet scale.
- A single click now selects on button release, not press (needed to tell clicks from drags).
- `MovementOrders` has no order counter, so the group acceptance cannot detect an identical repeated `Move` to a ship's own destination.
- A destroyed or deactivated selected ship stays in the selection until the next `SetSingle`, `Toggle`, `SetMany` or `Clear`; commands skip it and its ring hides.
- Right-clicking over a ship or obstacle orders the ground point beneath (ground mask only); there is no attack/follow or UI-over-pointer blocking.
- The unused project-wide template `InputSystem_Actions` binds `S` (`Player/Move`), `E` (`Player/Interact`) and `C` (`Player/Crouch`); nothing reads it. Revisit when shared controls are introduced.
- Scripted input events are only processed while the player window has focus (`runInBackground` off).
- `Assets/TutorialInfo/Icons/URP.png` is damaged in the working tree (not part of any change).
- The tactical camera has no map bounds and no camera collision (Issue #12 debt; until a real level needs it).
- Player and camera bindings are separate local actions with no input router; the S conflict was resolved by moving Stop to C (owner). Any new binding must be checked against both by hand.
- Camera keyboard paths are physical key positions (US layout names): the main-row zoom-in key is the `=`/`+` key.
- Camera pan speed is constant in world units at every zoom distance; the yaw direction convention (E and rightward drag clockwise from above) is provisional; final camera feel is UNDECIDED (owner).
- The camera rate check divides displacement by summed frame time, so it confirms delta-time scaling; it is not a wall-clock measurement.
- `CameraTest`'s pan-direction check (1°) is only meaningful at capped frame rates: run uncapped (about 950 fps, 0.014 u per frame) it measured 4.6° from float noise in the center-ray ground point; at 30/60/144 fps it measures 0.08–0.55°. Always run it with `-cameraFps`.
- Follow is a hard snap to the centroid every frame (no smoothing). F framing uses ship centers only, like box selection, so large hulls can extend past the 80 % frame; if the ships do not fit at `MaxDistance`, the distance stays at the maximum. A later aspect change does not reframe until F is pressed again.
- Destination circles are placeholder art for selected ships only; final appearance is UNDECIDED (owner).
- Camera scripted input needs the player window focused; an unfocused player pauses (`runInBackground` off). The scripted aspect change uses `Screen.SetResolution`, which has no effect in the Editor.
